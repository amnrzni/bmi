# QCXIS SSO — how it's wired here

Built against `SSO-INTEGRATION.md`. QCXIS is a standard OpenID Connect provider;
`App\Services\Sso\QcxisSsoDriver` implements Authorization Code + PKCE against it.

**Nothing is live until an app is registered and four env values are set.** Until then
`SSO_DRIVER=stub` runs the development picker, which refuses to work outside local/testing, and
admins use the email/password fallback.

## Turning it on

1. **Register the app** at `https://qcxis.com` → Console → Settings → **SSO apps**
   (`/console/settings/apps`). You need to be owner/admin of the org.
   - **App type: Confidential** — this is a server-side app. Do not pick Public.
   - **Redirect URI:** `https://<your-domain>/auth/sso/callback`
     Matched by **exact string comparison** — scheme, host, port, path and trailing slash all count.
     `…/callback` and `…/callback/` are different URIs.
   - `http://localhost:8000/auth/sso/callback` is accepted too, so the real flow can be tested from
     a laptop against production.
2. **Copy the client secret from the one-time reveal sheet.** It is stored as a hash and never shown
   again; losing it means deleting and recreating the app, which changes the `client_id`.
3. Set in `.env`:

   ```dotenv
   SSO_DRIVER=qcxis
   QCXIS_CLIENT_ID=c_0190a1b2c3d4…
   QCXIS_CLIENT_SECRET=…
   QCXIS_REDIRECT_URI=https://<your-domain>/auth/sso/callback
   ```

   `QCXIS_REDIRECT_URI` may be omitted if `APP_URL` is correct, but set it explicitly — an
   `APP_URL` typo becomes an exact-match failure that reads as "invalid_grant" with no clue why.
4. `php artisan config:clear`, then open `/login` — a **Continue with QCXIS** button appears.

## Decisions worth knowing

**PKCE is generated by hand, not by Socialite.** QCXIS requires `code_challenge_method=S256` on
*every* client including confidential ones, and Socialite setups commonly default PKCE off. That
mismatch fails at `/authorize` with an error that doesn't point at the cause. ~150 lines of driver
avoids the dependency and the trap.

**No `offline_access`, so no refresh tokens.** Sign-in mints a Laravel session and QCXIS is never
consulted again for that user. A refresh token would be a long-lived credential with nothing to do,
plus rotation and reuse-detection handling for no benefit. Scopes are `openid profile email`.

**Identity comes from `/userinfo`, not from verifying the id_token.** Both the token response and
userinfo arrive over direct server-to-server TLS from the issuer, which OIDC Core §3.1.3.7 accepts in
place of signature checking for the authorization-code flow. This keeps a JWT library and a JWKS
cache out of the project. Access tokens are opaque here and nothing decodes them.

**Unverified emails are refused** (`QCXIS_REQUIRE_VERIFIED_EMAIL`, default true). The roster match is
on email alone, so accepting an unverified address would let someone sign in as a colleague by
claiming their address. Turn it off only if QCXIS accounts legitimately carry unverified emails and
staff are locked out as a result — and understand what you're accepting.

**Endpoints come from the discovery document**, cached 24h, falling back to the documented paths
(`/v1/oauth/authorize`, `/v1/oauth/token`, `/v1/oauth/userinfo`) if it can't be reached. A discovery
blip shouldn't take sign-in down.

## The one thing that will break this

**QCXIS emails must match roster emails.** The entire identity match is
`lower(users.email) = lower(<email from QCXIS>)`. If QCXIS issues `firstname.lastname@qcxis.com` and
the roster holds `fname@qcxis.com`, every sign-in is rejected as "not on the challenge roster" and
the cause won't be obvious. Check one real account before rolling out.

## What happens on sign-in

| Step | Behaviour |
|---|---|
| `/auth/sso/redirect` | Generates PKCE verifier + `state`, stores both in the session, redirects to `/v1/oauth/authorize` |
| User declines consent | `?error=access_denied` → "sign-in was cancelled or could not be verified" |
| `/auth/sso/callback` | `state` compared with `hash_equals` and consumed; mismatch or absence is refused before any token call |
| Code exchange | Immediate, form-encoded, HTTP Basic client auth, identical `redirect_uri`, `code_verifier` |
| Identity | `GET /v1/oauth/userinfo`; email required, `email_verified` enforced |
| Roster match | Case-insensitive on email. No match → rejected, **never auto-created** |
| Leaver | `left_at` in the past → rejected |
| Success | Session regenerated (fixation guard), redirect to the originally intended page |
| First sign-in | Consent gate before any screen |

## Tests

`tests/Feature/QcxisSsoTest.php` — 18 tests covering the authorize URL shape, the PKCE derivation,
state mismatch/absence/replay, declined consent, token-exchange failure, verified-email enforcement,
discovery fallback, and two end-to-end sign-ins through the real route.

Run just those: `php artisan test --filter=QcxisSso`

## Not implemented, deliberately

- **Refresh tokens / `offline_access`** — not needed, see above
- **RP-initiated logout** (`POST /v1/oauth/logout`) — signing out ends the local session only; the
  QCXIS browser session persists, so the next sign-in may not re-prompt. Add `id_token_hint` handling
  if that matters
- **Introspection** — third-party clients get 403 anyway
- **`client_credentials`** — no machine-to-machine calls here
